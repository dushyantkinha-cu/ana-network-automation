# Unit Testing and Code Coverage — ANA Network Automation

## 1. Overview

The ANA Network Automation project uses automated unit testing and code coverage analysis to verify Python automation logic without requiring physical or simulated network devices during testing.

The implementation covers automation for Arista EOS, Cisco IOS-XE, Nokia SR Linux, NetBox inventory and configuration management, and the FastAPI management application.

The testing framework uses:

- **pytest 9.1.1** — Unit testing framework
- **pytest-cov 7.1.0** — pytest coverage integration
- **coverage.py 7.16.2** — Code coverage measurement
- **unittest.mock / pytest monkeypatch** — Simulation of external dependencies
- **Jenkins** — Automated CI execution
- **GitHub** — Source code version control and CI triggers

Unit tests exercise real Python application logic while mocking external boundaries, such as network connections, API requests, and configuration deployment operations.

No live network-device or external-service integration testing is required for this assignment.

## 2. Objective 1 — Unit Testing

### Implementation

The existing Python automation framework was extended with tests for:

- IP addressing, validation, and interface handling
- Network-device connection and platform selection
- NetBox inventory queries, pagination, and error handling
- Jinja2 configuration rendering and template validation
- Configuration collection and file handling
- Golden configuration comparison and promotion
- Configuration drift detection and reporting
- Automation validation workflows
- Arista, Cisco, and Nokia deployment logic
- FastAPI routes, services, and API clients
- Input validation and error handling

Tests are stored in the `tests/` directory.

Examples include:

| Test file | Purpose |
|---|---|

| `test_render_config.py` | Tests Jinja2 configuration rendering |
| `test_netbox_inventory.py` | Tests inventory processing and pagination |
| `test_device_connection.py` | Tests platform and connection logic |
| `test_compare_goldens.py` | Tests configuration comparison |
| `test_report_drift.py` | Tests configuration drift reporting |
| `test_arista_deployment.py` | Tests Arista deployment behavior |
| `test_cisco_deployment.py` | Tests Cisco deployment behavior |
| `test_nokia_deployment.py` | Tests Nokia deployment behavior |

Additional tests cover FastAPI routers, services, and integrations using mocked dependencies.

### Mocking approach

External systems are mocked so tests execute locally without making real changes.

For example, a configuration deployment test can simulate a successful device response or a deployment failure, then verify that the automation code handles that outcome correctly.

Similarly, NetBox API requests and Jenkins deployment calls are mocked to validate request construction, response handling, and safety checks.

This provides repeatable testing without depending on live infrastructure.

### Running unit tests

Activate the project environment:

```bash
cd ~/ana-network-automation
source .venv/bin/activate
```

Run an individual test module:

```bash
python -m pytest -q tests/test_validate_intent.py
```

Run rendering tests:

```bash
python -m pytest -q tests/test_render_config.py
```

The complete approved test suite is explicitly listed in the `Regression Tests` stage of the repository's `Jenkinsfile`.

This allowlist prevents protected or unrelated scripts from being collected unintentionally.

## 3. Objective 2 — Code Coverage Tool

### Implementation

A custom Python coverage auditing tool was created:

```text
scripts/coverage_audit.py
```

The tool reads execution data generated by `coverage.py` and examines Python source code using the standard-library `ast` module.

It reports:

1. Coverage percentage for individual Python modules.
2. Total functions identified in each module.
3. Number of functions whose executable bodies were exercised.
4. Function coverage percentage.
5. Names and locations of unexercised functions.
6. Modules with zero measured coverage.

### Coverage calculations

**Line coverage:**

```text
Line Coverage =
    Executed Statements / Total Executable Statements * 100
```

**Function coverage:**

```text
Function Coverage =
    Functions Exercised / Total Functions * 100
```

For example, if a module contains six functions and the tests exercise three function bodies, the tool reports 50% function coverage.

Function coverage is separate from statement and branch coverage.

A function being exercised does not necessarily mean that every possible behavior has been tested or that the test assertions prove correctness.

### Executing the coverage tool

The audit requires an existing coverage data file produced by the approved pytest suite.

Example:

```bash
COVERAGE_FILE=/tmp/ana-ci-coverage.data \
python scripts/coverage_audit.py \
/tmp/ana-coverage-audit.json
```

The tool prints the audit to the terminal and generates a JSON report.

Within Jenkins, these outputs are generated automatically.

### Zero-coverage verification

The coverage auditor was also tested using an isolated run of `test_validate_intent.py`.

Results:

- 28 tests passed.
- `automation/validate_intent.py` showed 96.3% line coverage.
- Automation modules not exercised by the isolated test run were reported at 0% coverage.

This demonstrated that the tool can identify untested modules rather than reporting only code that was executed.

## 4. Jenkins CI/CD Integration

The project uses the existing Jenkins CI job:

```text
ana-network-automation-ci
```

The pipeline definition is maintained in the repository's `Jenkinsfile`.

Jenkins automatically detects GitHub changes using SCM polling:

```groovy
pollSCM('H/5 * * * *')
```

This checks for repository changes on an approximately five-minute schedule.

### Pipeline workflow

1. Jenkins detects a new GitHub commit.
2. Jenkins checks out the source code.
3. A fresh Python virtual environment is created.
4. Development dependencies are installed.
5. Python syntax is checked.
6. Approved unit tests are executed.
7. Statement and branch coverage is calculated.
8. The custom module/function coverage auditor runs.
9. Coverage reports are archived as Jenkins artifacts.
10. Jenkins reports build success or failure to GitHub.

### Archived reports

Each successful testing build provides:

| Artifact | Purpose |
|---|---|
| `coverage.xml` | Machine-readable statement and branch coverage report |
| `coverage-audit.json` | Module and function-level coverage audit |
| `coverage-audit.txt` | Human-readable coverage audit |

These files can be accessed from the Jenkins build's Artifacts section.

The CI job does not deploy network configurations.

## 6. Scope and Limitations

The coverage measurement includes the version-controlled Python packages:

```text
automation/
webapp/
```

Other standalone operational scripts outside the measured packages are not included in the reported 94% coverage figure.

Therefore, 94% represents the configured measurement scope, not necessarily every Python script in the repository.

The test suite uses simulated dependencies and does not establish live network connectivity or prove that real devices and external APIs function correctly.

Those integrations are outside this assignment's selected testing scope.

## 7. Conclusion

The ANA Network Automation project successfully integrates automated unit testing, code coverage measurement, and Jenkins CI.

The implemented framework:

- Runs 790 automated tests.
- Measures statement and branch coverage.
- Reports module and function-level execution coverage.
- Identifies untested functions and modules.
- Generates reusable JSON and XML reports.
- Automatically runs in Jenkins following GitHub changes.
- Preserves live infrastructure by using mocked external dependencies.

This provides repeatable verification of the tested automation code and helps identify areas requiring additional unit testing.
